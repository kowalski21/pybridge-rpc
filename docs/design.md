# PyBridge — Design

**End-to-end type safety from Python to TypeScript — no codegen ceremony, no schema drift.**

PyBridge is a lightweight RPC framework that lets you define API procedures in Python with standard type hints and Pydantic models, then generates a fully typed TypeScript client automatically. Think tRPC/oRPC, but your backend is Python.

---

## The Problem

Full-stack teams using Python backends and TypeScript frontends live with a constant gap: you define your data models in Pydantic, then manually re-define them as TypeScript interfaces, then hope they stay in sync. OpenAPI helps, but the workflow is clunky — generate a spec, run a codegen tool, wire up a client, repeat every time a field changes.

oRPC and tRPC solved this elegantly for TypeScript-to-TypeScript stacks. There's no equivalent for Python-to-TypeScript.

## The Approach

Python's type system already carries everything we need at runtime. A function annotated with `(input: CreateUserInput) -> User` tells us the full contract — input schema, output schema, types, optionality, nesting. PyBridge extracts this information, builds a procedure registry, and generates TypeScript types and a typed client with a single command.

### Python Side

```python
from pybridge import Bridge
from pydantic import BaseModel

bridge = Bridge()

class CreateUserInput(BaseModel):
    name: str
    email: str
    age: int | None = None

class User(BaseModel):
    id: str
    name: str
    email: str

@bridge.procedure("users.create")
async def create_user(input: CreateUserInput) -> User:
    user = await db.users.create({**input.model_dump(), "id": uuid4().hex})
    return User(**user)

@bridge.procedure("users.list")
async def list_users() -> list[User]:
    return await db.users.find_many()

@bridge.procedure("health.ping")
async def ping() -> str:
    return "pong"
```

That's the entire backend definition. No `.input()` / `.output()` chains, no schema wrappers. The decorator registers the handler, introspects its type annotations, and builds the router tree from the dot-delimited path.

### Generated TypeScript Client

```bash
pybridge generate --out ./client/api.ts
```

Produces:

```typescript
// Auto-generated by PyBridge — do not edit

export interface CreateUserInput {
  name: string;
  email: string;
  age?: number | null;
}

export interface User {
  id: string;
  name: string;
  email: string;
}

export interface AppRouter {
  users: {
    create: (input: CreateUserInput) => Promise<User>;
    list: () => Promise<User[]>;
  };
  health: {
    ping: () => Promise<string>;
  };
}

export declare function createClient(baseUrl: string): AppRouter;
```

### Frontend Usage

```typescript
import { createClient } from "./api";

const api = createClient("http://localhost:8000");

const user = await api.users.create({ name: "Kofi", email: "kofi@example.com" });
//    ^ fully typed as User

const users = await api.users.list();
//    ^ fully typed as User[]
```

No manual type definitions. No OpenAPI-to-TypeScript pipeline. Change a Pydantic model, re-run generate, and TypeScript catches every downstream mismatch.

## Core Design

### Decorator-Based Registry

Procedures are registered via decorators with dot-delimited paths. Grouped sub-routers are supported for organization:

```python
users = bridge.group("users")

@users.procedure("create")
async def create_user(input: CreateUserInput) -> User:
    ...

@users.procedure("get")
async def get_user(input: GetUserInput) -> User:
    ...
```

### Type Introspection

PyBridge inspects function signatures at registration time — no need to declare input/output types separately. It supports:

| Python Type | TypeScript Output |
|---|---|
| `str` | `string` |
| `int`, `float` | `number` |
| `bool` | `boolean` |
| `None` | `null` |
| `list[X]` | `X[]` |
| `dict[str, X]` | `Record<string, X>` |
| `X \| None` / `Optional[X]` | `X \| null` |
| `Union[A, B]` | `A \| B` |
| `Literal["a", "b"]` | `"a" \| "b"` |
| `Enum` | string enum |
| `datetime` | `string` (ISO 8601) |
| `UUID` | `string` |
| `BaseModel` (nested) | named `interface` |
| `tuple[A, B, C]` | `[A, B, C]` |

### Transport

PyBridge serves procedures over HTTP (built on Starlette/ASGI). Each procedure maps to a POST endpoint:

```
POST /rpc/users.create   { "name": "Kofi", ... }  →  { "id": "...", "name": "Kofi", ... }
POST /rpc/users.list      (no body)                →  [{ ... }, { ... }]
```

The JS client is a `Proxy`-based wrapper around `fetch` that builds the path from property access and handles serialization/deserialization.

### Middleware

Procedures support middleware for auth, logging, and validation:

```python
@bridge.middleware
async def auth(ctx, next):
    token = ctx.headers.get("authorization")
    ctx.user = await verify_token(token)
    return await next(ctx)

@bridge.procedure("users.create", middlewares=[auth])
async def create_user(input: CreateUserInput, ctx: Context) -> User:
    ...
```

### Error Handling

Typed errors that propagate to the client:

```python
from pybridge import ProcedureError

@bridge.procedure("users.get")
async def get_user(input: GetUserInput) -> User:
    user = await db.users.find(input.id)
    if not user:
        raise ProcedureError(code="NOT_FOUND", message="User not found")
    return user
```

```typescript
try {
  const user = await api.users.get({ id: "abc" });
} catch (e) {
  if (e.code === "NOT_FOUND") { ... }  // typed error codes
}
```

## Architecture

```
┌─────────────────────────────────────────────┐
│  Python Backend                             │
│                                             │
│  @bridge.procedure("users.create")          │
│  async def create_user(input: X) -> Y       │
│       │                                     │
│       ▼                                     │
│  ┌──────────┐    ┌───────────────────┐      │
│  │ Registry │───▶│ Type Introspection │      │
│  │ (tree)   │    │ (Pydantic → JSON  │      │
│  └──────────┘    │  Schema → TS)     │      │
│       │          └───────────────────┘      │
│       ▼                    │                │
│  ┌──────────┐              ▼                │
│  │ ASGI App │    ┌──────────────────┐       │
│  │ (HTTP)   │    │ CLI: generate    │       │
│  └──────────┘    │ → types.ts       │       │
│                  │ → client.ts      │       │
│                  └──────────────────┘       │
└─────────────────────────────────────────────┘
         ▲                       │
         │ POST /rpc/*           │ imports
         │                       ▼
┌─────────────────────────────────────────────┐
│  TypeScript Frontend                        │
│                                             │
│  const api = createClient("http://...")     │
│  const user = await api.users.create({...}) │
│  //    ^ User type flows from Python        │
└─────────────────────────────────────────────┘
```

## Why Not Just Use FastAPI + openapi-typescript?

That works. But it's a multi-step pipeline: FastAPI → OpenAPI spec → codegen → typed client → wire it up. Every model change requires re-running the pipeline and hoping the generated code plays nicely with your frontend.

PyBridge collapses this into one step. Your Python function signature *is* the API contract. The TypeScript types are a direct projection of your Pydantic models, not an interpretation of an intermediate OpenAPI spec. The client is a thin proxy, not a generated SDK with its own opinions about method names and return types.

The goal is the same DX that tRPC/oRPC developers enjoy — but with Python as the source of truth.
